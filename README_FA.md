# J+Rock

[English](README.md) | **فارسی**

یک دستیار برنامه‌نویسی عاملی (agentic) صادق و پیگیر، با یک **موتور معاملاتی فیوچرز USDT-M باینکس** که در بدنه و روحش تعبیه شده است.

- **روح**: باهوش، هرگز دروغ نمی‌گوید، وقتی چیزی را نمی‌داند می‌گوید «نمی‌دانم»، شکارچی بی‌امان باگ، با لحنی مستقیم.
- **دسترسی کامل به ابزارها**: شل، خواندن/نوشتن/وصلهٔ فایل، جستجوی کد، گیت، HTTP و فرایندها.
- **خودتعمیری**: کد خودش و موتور معاملاتی را بازرسی، عیب‌یابی و اصلاح می‌کند. هر ویرایش خودکار با مجوز انجام می‌شود (`auto accept edit on|off`).
- **حلقهٔ یادگیری**: بازخورد کاربر و رویدادهای گذشته ذخیره و بعداً بازیابی می‌شوند.
- **موتور معاملاتی**: ۳۷ اندپوینت REST (از ۳۹ اندپوینت مستند)، وب‌سوکت عمومی و خصوصی، ۱۶ استراتژی یکتا در ۵ دسته، تجمیع چند تایم‌فریمی، حد سود/حد ضرر با تصمیم عامل و رتبه‌بندی خودکار نمادها.

> این نسخهٔ فارسی همراه نسخهٔ انگلیسی نگهداری می‌شود. اگر جایی اختلاف دیدید، [`README.md`](README.md) مرجع اصلی است.

## شروع سریع

```bash
cd jrock
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # then fill in your keys
python -m jrock.cli
```

در اولین اجرا، **AutoSetModelByKey** مقادیر `BASE_URL` و `API_KEY` را از `.env` می‌خواند، `GET {BASE_URL}/models` را صدا می‌زند، گزینه‌های برتر را با یک درخواست چت واقعی آزمایش می‌کند و بهترین مدل سالم را در `.env` ثبت می‌کند.

```bash
python -m jrock.cli --startup          # اجرای بررسی‌های شروع و خروج
python -m jrock.cli --once "/check_system"
python -m jrock.cli --help-cmds
```

## رابط‌ها: CLI و تلگرام

موتور دو رابط دارد و هیچ رابط وب ندارد. هر دو از همان روتر `JRockAgent.handle()` استفاده می‌کنند؛ بنابراین فرمان‌ها، زبان طبیعی و تأییدهای `yes`/`no` در هر دو یکسان رفتار می‌کنند.

```bash
python -m jrock.cli                # REPL تعاملی ترمینال
python -m jrock.telegram_bot       # long polling در تلگرام (TELEGRAM_BOT_TOKEN)
python -m jrock.cli --once "/status"
```

ربات تلگرام یک نمایش‌دهندهٔ نازک روی `build_state()` در `jrock/state.py` است؛ یک عکس فوری فقط‌خواندنی از موتور، حساب، پوزیشن‌ها و سفارش‌ها، به‌همراه روتر فرمان‌ها. فرمان‌های `/status /positions /orders /pnl /engine /tpsl /help` در منوی تلگرام منتشر می‌شوند و از یک فهرست واحد ساخته می‌شوند تا منو و `/help` هرگز با هم اختلاف پیدا نکنند. چون از long polling استفاده می‌شود، نه URL عمومی لازم است، نه TLS و نه پورت باز.

## خودتعمیری

`python -m jrock.self_heal --once` یک چرخهٔ تعمیر را اجرا می‌کند:

1. `pytest -q tests`
2. اگر سبز بود، چیزی برای تعمیر نیست؛
3. اگر قرمز بود، خروجی تست‌های شکست‌خورده و بخش‌های مرتبط فایل‌ها به مدل تنظیم‌شده (`agent.chat`) فرستاده می‌شود، با پرامپت سختگیرانهٔ «فقط JSON برگردان» و درخواست جایگزینی رشته‌های دقیق؛
4. اصلاح فقط وقتی اعمال می‌شود که لنگر (anchor) دقیقاً یک بار پیدا شود؛ حداکثر ۵ فایل در هر چرخه؛
5. تست‌ها دوباره اجرا می‌شوند: اگر باز هم قرمز شد، همهٔ تغییرها برگردانده می‌شوند؛ اگر سبز شد، فایل‌های تغییرکرده commit و به `origin main` push می‌شوند.

`python -m jrock.self_heal --loop` این کار را هر `SELF_HEAL_INTERVAL_HOURS` تکرار می‌کند (پیش‌فرض ۶، مقدار ۰ = خاموش). این حلقه هرگز به `.env`، `data/` یا خارج از `jrock/` و `tests/` دست نمی‌زند، هرگز force-push نمی‌کند و فقط روی `main` push می‌کند.
در زمان اجرا: `/selfheal once|loop|stop|status`.

## چت تلگرام

`python -m jrock.telegram_bot` همان عامل در یک چت تلگرام است؛ بنابراین می‌توانید ربات را از گوشی کنترل کنید بدون این‌که هیچ پورتی روی سرور باز باشد. هر خطی که دریافت می‌شود از همان `JRockAgent.handle()` عبور می‌کند و هر عددی از همان عکس فوری `build_state` (`jrock/state.py`) می‌آید؛ بنابراین نمایشگر هرگز از موتور جدا نمی‌افتد.

```bash
export TELEGRAM_BOT_TOKEN=123456:ABC...   # from @BotFather
python -m jrock.telegram_bot
```

اولین پیام از چت اپراتور، شناسهٔ آن چت را چاپ می‌کند. آن را در `TELEGRAM_ALLOWED_CHATS` قرار دهید تا محدود کنید ربات به کدام چت‌ها پاسخ دهد (خالی بگذارید تا به هر چتی که ربات را پیدا کند پاسخ دهد، یا چند چت را با `id1,id2` جدا کنید). چتی که در فهرست نباشد هیچ پاسخی نمی‌گیرد؛ حتی پیام خطا.

### فرمان‌های منو

کل فهرست فرمان‌ها هنگام شروع در دکمهٔ Menu تلگرام منتشر می‌شود، پس بدون تایپ `help` هم دیده می‌شود. ده فرمان موتور همان‌هایی هستند که هر دقیقه استفاده می‌شوند:

| فرمان | کار |
|---|---|
| `/status` | موتور + حساب + پوزیشن‌ها |
| `/positions` | پوزیشن‌های باز |
| `/orders` | سفارش‌های در انتظار |
| `/pnl` | حساب و سود/زیان |
| `/report` | تولید و ارسال فوری یک گزارش موتور |
| `/tpsl` | روش TP/SL و وضعیت پله‌ها: نمایش/تنظیم (`/tpsl pending BTCUSDT`) |
| `/balance` | موجودی و مصرف مارجین |
| `/price` | آخرین قیمت / قیمت مارک نمادها |
| `/engine` | وضعیت کلیدهای موتور |
| `/help` | همهٔ موارد بالا به‌همراه صفحه‌های موضوعی `<topic>` |

هر چیز دیگری که در چت تایپ شود، عیناً به روتر موتور می‌رود؛ بنابراین عبارت‌های زبان طبیعی و فرمان‌هایی که CLI می‌پذیرد (از جمله `/think`، `/code`، `/selfheal` و فرمان‌های معاملاتی) اینجا هم کار می‌کنند؛ فقط دکمهٔ منو ندارند.

### ارسال گزارش

حلقهٔ گزارش موتور گزارش را روی stdout چاپ می‌کند؛ ربات تلگرام کانال دوم و فعال همان گزارش است:

```text
report on                 -> گزارش‌ها هر report_interval به چت push می‌شوند
/report                   -> یک گزارش فوری، مستقل از کلید روشن/خاموش
```

- گزارش فقط به چت‌هایی push می‌شود که قبلاً به ربات پیام داده‌اند؛ چتی که هرگز پیام نداده، گزارشی نمی‌گیرد.
- با گفتن `report off` ارسال فوراً متوقف می‌شود.
- `report_interval` یک کف ۵ ثانیه‌ای دارد تا مقدار اشتباه باعث سیل پیام در تلگرام نشود.
- خطا در تولید گزارش ثبت و جذب می‌شود؛ بازهٔ بعدی دوباره تلاش می‌کند.

### هشدارهای معاملاتی

ربات لاگ معاملات خود موتور (`data/trades.jsonl`) را می‌پاید و همان لحظه‌ای که پوزیشنی باز یا بسته می‌شود پیام می‌فرستد — بدون نیاز به گزارش دوره‌ای:

| هشدار | چه چیزی دارد |
|---|---|
| **POSITION OPENED** | نماد، جهت، مقدار، ورود، اطمینان/قدرت، SL/TP و شناسهٔ سفارش |
| **POSITION CLOSED** | نماد، شناسهٔ پوزیشن و **دلیل** (`user`، `account_tp`، `account_sl`، `reversal`) |
| **POSITION CLOSED ON EXCHANGE** | برخورد TP/SL بومی (یا بستن دستی) که در تطبیق تشخیص داده شده، همراه جهت، مقدار و ورود |
| **CLOSE FAILED** | صرافی بستن را رد کرده و خطا آمده است — تنها شکستی که نباید منتظر گزارش بماند |

هشدارها به همهٔ چت‌هایی می‌روند که در همین اجرا به ربات پیام داده‌اند. اولین بررسی از انتهای فایل شروع می‌شود، پس ری‌استارت هرگز معامله‌های قدیمی را دوباره نمی‌فرستد. چون منبع، همان `data/trades.jsonl` مشترک است، موتور می‌تواند در فرایندی جدا از ربات اجرا شود، به شرطی که هر دو از یک پوشهٔ `data/` استفاده کنند.

### تجمیع

- یک رأی فقط وقتی شمرده می‌شود که `confidence >= tf_min_confidence` باشد (پیش‌فرض ۶۰).
- یک معامله به `>= min_agreeing` استراتژی **متمایز** (پیش‌فرض ۳) در یک سمت نیاز دارد.
- اطمینان تجمیعی باید `>= min_confidence` باشد (پیش‌فرض ۷۰).
- اطمینان = میانگین وزن‌دار تایم‌فریم + پاداش توافق + پاداش چند تایم‌فریمی − جریمهٔ تضاد.
- یک استراتژی که در ۳ تایم‌فریم هم‌نظر است هنوز **یک** استراتژی است (چند تایم‌فریمی اطمینان را بالا می‌برد، نه تعداد را).

## رتبه‌بندی خودکار جهان نمادها (Universe auto-ranking)

موتور به‌جای اسکن یک واچ‌لیست ثابت می‌تواند نمادهایش را از کل جهان نمادهای قابل‌معامله انتخاب کند. برای این کار همهٔ تیکرها را از اندپوینت عمومی `get_tickers` می‌گیرد، بر اساس حجم معاملات ۲۴ ساعته فیلتر می‌کند، با روش انتخابی رتبه‌بندی می‌کند و `UNIVERSE_SIZING` نماد برتر را اسکن می‌کند.

| روش | معیار رتبه‌بندی |
|---|---|
| `GAINERS` | درصد تغییر نسبت به باز شدن ۲۴ ساعته، از بیشترین |
| `LOSERS` | درصد تغییر نسبت به باز شدن ۲۴ ساعته، از کمترین |
| `VOLUME` | حجم معاملات ۲۴ ساعته به USDT، از بیشترین |
| `MOVERS` | قدر مطلق درصد تغییر نسبت به باز شدن ۲۴ ساعته، از بیشترین |

`GAINERS` / `LOSERS` / `MOVERS` بر اساس **درصد** رتبه‌بندی می‌کنند، نه تغییر مطلق قیمت: حرکت ۶۰ دلاری بیت‌کوین بزرگ‌تر از رشد ۳۰ درصدی یک جفت‌ارز ارزان نیست. تیکر کهنه‌ای که آخرین قیمتش صفر است نادیده گرفته می‌شود، نه این‌که به‌عنوان بازندهٔ ۱۰۰− درصد رتبه بگیرد.

```
universe rank GAINERS|LOSERS|VOLUME|MOVERS   # انتخاب روش
universe sizing 20                          # اسکن ۲۰ نماد برتر (۱ تا ۲۰۰)
universe volume 1000000                     # کف حجم ۲۴ ساعته به USDT
universe rank auto                          # روشن؛ روش فعلی حفظ می‌شود، در نبود روش VOLUME
universe rank off                           # خاموش (اندازهٔ تنظیم‌شده حفظ می‌شود)
```

املای قدیمی `LOOSERS` هنوز پذیرفته می‌شود، اما روش رسمی `LOSERS` است. `universe rank auto` اندازه را **صفر نمی‌کند**؛ اگر اندازه صفر باشد صریح می‌گوید که چیزی اسکن نمی‌شود.

پیکربندی در `.env`:

| متغیر | معنی |
|---|---|
| `UNIVERSE_RANK` | `GAINERS` \| `LOSERS` \| `VOLUME` \| `MOVERS`؛ خالی = خاموش |
| `UNIVERSE_SIZING` | تعداد نمادهای برتر برای اسکن (۱ تا ۲۰۰؛ `0` = خاموش) |
| `MIN_24H_VOLUME_USD` | کف حجم معاملات ۲۴ ساعته به USDT؛ `0` = بدون کف |

رتبه‌بندی فقط وقتی فعال است که **هم** روش و **هم** اندازهٔ غیرصفر تنظیم شده باشند (مقدار زمان اجرا در `data/state.json` بر `.env` اولویت دارد). در این حالت، واچ‌لیست ثابت `TRADE_SYMBOLS` برای اسکن جایگزین می‌شود؛ اما فید وب‌سوکت همچنان نمادهای تنظیم‌شده و پوزیشن‌های باز را قیمت‌گذاری می‌کند. `/settings` مقادیر `universe rank`، `universe sizing` و `min 24h volume` را نشان می‌دهد.

## حد سود/حد ضرر — تصمیم با عامل

شما فقط **دو** عدد تنظیم می‌کنید:

- `breakeven threshold pct` — وقتی ROI به این مقدار رسید، حد ضرر را به نقطهٔ ورود منتقل کن.
- `trailing trigger stop ROI pct` — وقتی ROI به این مقدار رسید، استاپ متحرک را شروع کن.

بقیه چیزها محاسبه می‌شوند:

1. **قیمت لیکویید** از فرمول مارجین ایزوله با نرخ واقعی مارجین نگهداری برای همان پلهٔ نوشنال پوزیشن:
   - لانگ: `liq = entry * (1 - 1/L + mmr)`
   - شورت: `liq = entry * (1 + 1/L - mmr)`
2. **حد ضرر** به اندازهٔ `liq sl distance pct` (پیش‌فرض ۵۰٪) از مسیر ورود تا لیکویید قرار می‌گیرد؛ یعنی تقریباً در ۵۰٪ ROI‌ای که لیکویید هزینه می‌کرد فعال می‌شود.
3. **حد سود** = فاصلهٔ حد ضرر × مضرب R، مقیاس‌شده با قدرت سیگنال:
   `weak 1.2R · normal 1.8R · strong 2.5R · extreme 3.2R` و کمی تنظیم‌شده با اطمینان.
4. **اندازه** از ریسک: `qty = (equity × risk_pct) / |entry − stop|`، محدود به حداکثر نوشنال و گرد‌شده به **پایین** بر اساس `basePrecision`.

حد سود/حد ضرر به سفارش ورود متصل می‌شوند (`tpPrice`/`slPrice` در `place_order`) و بعداً برای سر‌به‌سر و استاپ متحرک با `modify_position_tp_sl_order` جابه‌جا می‌شوند.

## نکات مهم باینکس

**امضای REST** (رسمی):

```
message = nonce + timestamp + apiKey + queryString + body
digest  = sha256(message)
sign    = sha256(digest + secretKey)
```

هدرها: `api-key`، `sign`، `nonce`، `timestamp`، `language`، `Content-Type`.
بدنه باید JSON فشرده با کلیدهای مرتب باشد؛ query string نیز مرتب و urlencode شود.

**ورود وب‌سوکت**: `sign = sha256(sha256(timestamp + nonce + apiKey) + secretKey)` و timestamp بر حسب **ثانیه**.

**`qty` مقدار ارز پایه است**، نه قرارداد. `minTradeVolume` / `maxMarketOrderVolume` نیز مقدار ارز پایه‌اند. مقدار qty را به پایین با `basePrecision` و قیمت را با `quotePrecision` گرد کنید.

**خطای 10011** (اختلاف زمان) خودکار مدیریت می‌شود: کلاینت ساعت را دوباره همگام می‌کند و یک بار تلاش می‌کند.

**شکل پاسخ‌ها همیشه مطابق صفحهٔ مستندات نیست.** دموی رسمی (`FuturesPrivateApiClient.java`) نوع `POST /api/v1/futures/tpsl/place_order` را `List<OrderIdResp>` می‌داند، در حالی که خود `place_order` یک `OrderIdResp` است؛ و سرور زنده از دمو پیروی می‌کند، نه از صفحهٔ مستندات (که یک object نشان می‌دهد). `client.order_row()` هر دو را در مرز کلاینت به یک dict تبدیل می‌کند. پیش از این اصلاح، موتور روی آرایه `(res or {}).get("orderId")` می‌خواند و **بعد از ثبت اولین پلهٔ نردبان** با `AttributeError: 'list' object has no attribute 'get'` می‌مرد: یک حد سود به‌جای سه حد سودِ نردبان، و یک حلقهٔ اسکن مرده.

**خطای 10002** (Parameter error) به‌صورت محلی جلوگیری می‌شود. هر بدنهٔ سفارش توسط `jrock/trader/order_builder.py` ساخته می‌شود که هر فیلد را **قبل از ارسال** با مشخصات رسمی اعتبارسنجی می‌کند و به‌جای فرستادن درخواست خراب، یک خطای محلی نام‌دار پرتاب می‌کند:

| فیلد | قاعدهٔ اعمال‌شده |
|---|---|
| `symbol` | باید در فهرست زندهٔ `trading_pairs` باشد (وگرنه نزدیک‌ترین گزینه‌ها پیشنهاد می‌شود) |
| `side` | `BUY` \| `SELL` (نرمال‌شده از نظر حروف بزرگ/کوچک) |
| `orderType` | `LIMIT` \| `MARKET` (نرمال‌شده) |
| `tradeSide` | `OPEN` \| `CLOSE` (نرمال‌شده). **در حالت one-way حذف می‌شود** — مستندات می‌گویند فقط در حالت hedge لازم است |
| `effect` | `GTC` \| `IOC` \| `FOK` \| `POST_ONLY`، فقط برای LIMIT |
| `qty` | رشته، `>= minTradeVolume`، `<= maxMarketOrderVolume`، قالب‌بندی با `basePrecision` |
| `price` | رشته، برای LIMIT لازم، برای MARKET **حذف**، قالب‌بندی با `quotePrecision` |
| `positionId` | وقتی `tradeSide == CLOSE` لازم است؛ هرگز بدون `tradeSide` فرستاده نمی‌شود |
| `reduceOnly` | بولی |
| `tpPrice`/`slPrice` | رشته، قالب‌بندی با `quotePrecision` |
| `clientId` | حروف و ارقام، حداکثر ۳۲ کاراکتر |

> **داستان 10002 در AKEUSDT.** نماد `AKEUSDT` مقدار `basePrecision: 0` دارد؛ یعنی qty باید **صحیح** باشد. تابع `PairRules.from_api` از `int(d.get(k, default) or default)` استفاده می‌کرد و چون `0` در پایتون falsy است، دقت واقعی `0` بی‌صدا با پیش‌فرض `4` جایگزین می‌شد. بعد موتور `"qty":"1686.3406"` می‌فرستاد و صرافی رد می‌کرد. اصلاح: خواندن مقدار بدون تبدیل `or` و قالب‌بندی qty با `format_qty()` (که `basePrecision 0` را به‌صورت عدد صحیح می‌نویسد).

برای دیدن بدنهٔ دقیق سفارش کنار هر خطا، `BITUNIX_DEBUG_ORDER=true` را تنظیم کنید.

## سطح تفکر (`/think`)

`/think` تعیین می‌کند **مدل قبل از پاسخ چقدر استدلال کند**. این یک **تنظیم** است، نه حالت چت.

**برای صحبت با عامل به `/think` نیازی ندارید.** عادی تایپ کنید و عامل پاسخ می‌دهد. `/think` فقط شدت فکر کردن را تغییر می‌دهد.

| سطح | معنی |
|---|---|
| `off` | بدون استدلال، سریع‌ترین و ارزان‌ترین |
| `low` | استدلال کوتاه |
| `medium` | پیش‌فرض — متعادل |
| `high` | استدلال بلند، توکن بیشتر |
| `max` | عمیق‌ترین استدلال، بیشترین توکن، کندترین |

```
/think              نمایش سطح فعلی و توضیح آن
/think status       همان بالا
/think high         تنظیم سطح (ماندگار)
```

نام‌های جایگزین: `none`->`off`، `min`->`low`، `med`->`medium`، `hi`->`high`، `maximum`->`max`. حروف بزرگ/کوچک مهم نیست. سطح نامعتبر فهرست معتبر و نزدیک‌ترین گزینه را چاپ می‌کند و هرگز کرش نمی‌کند.

**محل ذخیره.** `data/settings.json` (ماندگار پس از ری‌استارت) و آینه‌شده در `THINKING_LEVEL=` داخل `.env`. پیش‌فرض `medium` است. اولویت در خواندن: store > `.env` > پیش‌فرض.

**چه چیزی واقعاً فرستاده می‌شود.** سطح به یک پارامتر واقعی ارائه‌دهنده نگاشت می‌شود که از فرادادهٔ `/models` خود مدل انتخاب می‌شود، نه حدس:

| سطح | `reasoning_effort` (سازگار با OpenAI) | `thinking_budget` (سبک بودجه‌ای) |
|---|---|---|
| `off` | *چیزی فرستاده نمی‌شود* | *چیزی فرستاده نمی‌شود* |
| `low` | `low` | `1024` |
| `medium` | `medium` | `4096` |
| `high` | `high` | `16384` |
| `max` | `high` | `32768` |

`off` هیچ پارامتر استدلالی نمی‌فرستد. مدلی که پشتیبانی از استدلال را اعلام نکند هم **هیچ پارامتری** نمی‌گیرد؛ هرگز فیلد پشتیبانی‌نشده نمی‌فرستیم تا درخواست با 400 رد شود. سطح و پارامتر واقعی در سطح debug لاگ می‌شوند.

**بودجهٔ خروجی.** سطح تفکر بالا به فضای اضافی برای توکن‌های استدلال **روی** پاسخ نیاز دارد؛ بنابراین `max_tokens` با سطح مقیاس می‌گیرد (`off` 800، `low` 1200، `medium` 2000، `high` 6000، `max` 12000). اگر سقف تنظیم‌شده از بودجهٔ تفکر کمتر باشد، هشدار ثبت می‌شود؛ همین ترکیب است که پاسخ خالی تولید می‌کند.

## مسیر پردازش هر خط

هر خطی که تایپ می‌کنید از شش مرحله به این ترتیب عبور می‌کند:

1. یک اقدام مخرب در انتظار `yes`/`no` -> تأیید یا لغو
2. `/command` -> توزیع‌کنندهٔ فرمان‌های عامل
3. یک کلمهٔ تنها که نام فرمان عامل است (`balance`، `positions`، `help`، ...) -> عامل
4. گرامر فرمان موتور (`leverage 20`، `scan off`، `min agreeing strategies 3`) -> موتور
5. یک جملهٔ زبان طبیعی -> لایهٔ نیت (`jrock/nlu.py`)
6. هر چیز دیگر -> مدل، به‌عنوان زبان طبیعی

کلمه‌ای که هم پرسش و هم تنظیم‌کننده است با آرگومانش تفکیک می‌شود: `leverage` می‌خواند، `leverage 20` تنظیم می‌کند. `report` وضعیت را می‌خواند، `report on` گزارش موتور را روشن/خاموش می‌کند.

**کلمات معاملاتی هرگز به مدل فرستاده نمی‌شوند.** `balance`، `bal`، `wallet`، `equity`، `funds`، `positions`، `orders`، `price`، `funding`، `leverage`، `margin`، `pnl`، `status`، `symbols`، `pairs`، `markets` همگی هندلر واقعی دارند.

## زبان طبیعی (بدون نیاز به فرمان)

لازم نیست فرمان تایپ کنید. یک جملهٔ معمولی به **همان رشتهٔ فرمانی** که می‌توانستید تایپ کنید تبدیل می‌شود و به روتر موجود تحویل داده می‌شود؛ لایهٔ نیت هرگز هندلر را دوباره پیاده‌سازی نمی‌کند، فقط تصمیم می‌گیرد جمله **کدام** فرمان را می‌خواهد.

| شما می‌نویسید | اجرا می‌شود |
|---|---|
| `show me my trading settings` | `settings trade` |
| `what is my balance` | `balance` |
| `show my positions` | `positions` |
| `what are my open orders` | `orders` |
| `what is my pnl` | `pnl` |
| `show me the status` | `status` |
| `turn off autotrade` | `stop trading` |
| `stop the engine` | `engine off` |
| `close my AKEUSDT position` | `close position AKEUSDT` |
| `set leverage to 5x` | `leverage 5` |
| `set risk to 2%` | `risk 2.0` |
| `why did the last order fail` | لاگ خطای موتور + راهنمای کد |
| `what does TP_SL_MIN_STOP_TICKS do` | پاسخ از `jrock/config.py` |

جمله‌های فارسی هم پشتیبانی می‌شوند (مثلاً «پوزیشنم رو ببند»، «موجودی من چقدره»، «اهرم رو ببر ۵»).

**ایمنی.** هر چیزی که پول جابه‌جا می‌کند — باز یا بسته کردن پوزیشن، تغییر اهرم، ریسک، حالت مارجین، حالت پوزیشن، autotrade یا موتور — در نوبت اول **اجرا نمی‌شود**. موتور چاپ می‌کند که چه کاری می‌خواهد انجام دهد و منتظر `yes` صریح می‌ماند. `no` لغو می‌کند. اقدام در انتظار فقط در حافظه است، پس از ری‌استارت زنده نمی‌ماند.

**پرسش در ابهام.** `close my position` می‌پرسد کدام نماد. `set my leverage` مقدار را می‌پرسد. `open a position on BTCUSDT` می‌پرسد لانگ یا شورت. دستور مستقیم `open long BTCUSDT` فهمیده می‌شود اما **رد می‌شود**: موتور اندازهٔ هر سفارش را از سیگنال و تنظیم ریسک شما می‌سازد و اختراع اندازه از یک جمله، حدس با پول واقعی است.

**متن آزاد همچنان به مدل می‌رسد.** جمله‌ای که لایهٔ نیت نمی‌شناسد بدون تغییر عبور می‌کند، پس هیچ چیز سالمی از کار نمی‌افتد.

**موتور دربارهٔ تنظیمات خودش پاسخ می‌دهد.** `TP_SL_MIN_STOP_TICKS`، `TAKER_FEE_RATE` و `MARGIN_SAFETY_PCT` در `jrock/config.py` تعریف شده‌اند؛ پرسش دربارهٔ آن‌ها از مخزن و با مقدار زنده پاسخ داده می‌شود. موتور هرگز ادعا نمی‌کند کد خودش را نمی‌بیند.

## پاسخ‌های خالی مدل

یک completion خالی یک **شکست** است، نه پاسخ عادی. CLI علت را تشخیص می‌دهد و نام می‌برد:

| علت | معنی |
|---|---|
| `length_zero_tokens` | قبل از تولید هر چیزی به سقف توکن خورد |
| `length_reasoning_only` | همهٔ توکن‌های completion توکن استدلال بودند |
| `length_no_text` | به سقف خورد و متنی تولید نشد |
| `content_filter` | ارائه‌دهنده خروجی را مسدود کرد |
| `tool_call_only` | مدل فراخوانی ابزار می‌خواست و متن ننوشت |
| `no_choices` | HTTP 200 با آرایهٔ خالی `choices` |
| `error_in_200` | ارائه‌دهنده شیء خطا را داخل پاسخ 200 برگرداند |
| `whitespace_only` | محتوا فقط فاصله بود |

برای دو علت `length`، CLI **یک بار با `thinking=off` دوباره تلاش می‌کند** و به شما می‌گوید. اگر تلاش دوم هم شکست بخورد، علت، finish reason، تعداد توکن‌ها، `max_tokens` تنظیم‌شده و اقدام بعدی را می‌گیرید؛ هرگز `(model returned an empty message)`.

**کدام سطح را استفاده کنید.** `off`/`low` برای چت سریع. `high`/`max` برای دیباگ، بازبینی کد یا تحلیل استراتژی — مسائل سخت‌تر، اما کندتر و پرتوکن‌تر.

## وب‌سوکت (`/ws`)

موتور می‌تواند قیمت‌های زنده را به‌جای polling از REST از وب‌سوکت باینکس بگیرد. `MARKET_DATA_SOURCE=rest|ws` (پیش‌فرض **`rest`**) منبع را انتخاب می‌کند؛ `/ws on` و `/ws off` آن را در زمان اجرا عوض می‌کنند و انتخاب را ذخیره می‌کنند.

```
/ws            وضعیت اتصال، uptime، اتصال‌های مجدد، کانال‌ها، تعداد پیام‌ها
/ws on|off     تغییر منبع دادهٔ بازار (ذخیره می‌شود)
/ws test       باز کردن اتصال واقعی، چاپ ۳ فریم خام اول، بستن
```

### چه چیزی قبلاً واقعاً خراب بود

فایل قدیمی `ws.py` **کد مرده** بود — هیچ‌جا import نمی‌شد — و همهٔ نام‌های کانال عمومی در آن غلط بودند. سرور نام کانال غلط را می‌پذیرد، `{"op":"connect","data":{"result":true}}` پاسخ می‌دهد و بعد هرگز چیزی push نمی‌کند؛ بنابراین شکست بی‌صدا بود.

| قدیمی (غلط) | درست | نتیجهٔ زنده |
|---|---|---|
| `market_price` | `price` | قدیمی: ۰ فریم، جدید: `mp`/`ip`/`fr` واقعی |
| `market_ticker` | `ticker` | قدیمی: ۰ فریم، جدید: `la`/`o`/`h`/`l` واقعی |
| `market_tickers` | `tickers` | قدیمی: ۰ فریم، جدید: آرایهٔ واقعی |
| `market_trade` | `trade` | قدیمی: ۰ فریم، جدید: معاملات واقعی |
| `market_kline_1hour` | `market_kline_60min` | قدیمی: `data={}`، جدید: OHLC واقعی |

### کش قیمت — چطور `ws` واقعاً جای REST را می‌گیرد

`MARKET_DATA_SOURCE=ws` فقط یک برچسب نیست. هر خواندن قیمت در موتور از یک مسیر واحد به نام `TraderEngine.get_price(symbol)` عبور می‌کند که `PriceCache` تغذیه‌شده از کانال‌های عمومی `price` و `ticker` را می‌بیند.

| وضعیت | چه اتفاقی می‌افتد |
|---|---|
| نقل‌قول کش‌شده جوان‌تر از `max_age` کش قیمت (پیش‌فرض ۵ ثانیه) | برگردانده می‌شود، `source=ws`، **بدون فراخوانی REST** |
| نقل‌قول کش‌شده وجود ندارد | بازگشت به REST، به‌عنوان `miss` شمرده می‌شود |
| نقل‌قول کش‌شده قدیمی‌تر از حد | **رد می‌شود**، هشدار ثبت، بازگشت به REST، `stale_rejection` |
| WS قطع است | بازگشت به REST؛ موتور ادامه می‌دهد و هرگز روی سوکت بلاک نمی‌شود |
| `MARKET_DATA_SOURCE=rest` | هیچ کشی خوانده نمی‌شود، **هیچ سوکتی باز نمی‌شود** |

هر نقل‌قول منبع، زمان صرافی و زمان دریافت محلی را همراه دارد، بنابراین قیمت کهنه هرگز بی‌صدا برای تصمیم معاملاتی استفاده نمی‌شود.

`/ws` شمارنده‌های کش (`hits`، `misses`، `stale_rejections`، `rest_fallbacks`، `ws_updates`، `rest_updates`) و کل فراخوانی‌های قیمت REST را چاپ می‌کند؛ همین است که ثابت می‌کند REST واقعاً دور زده می‌شود.

تأیید زنده (`scripts/verify_ws_prices.py`، فید واقعی):

```
Market data: ws (connected, 2 symbols)
BTCUSDT: 75921.8 src=ws age=0.06s exchange_ts=1794010712.343
20 get_price calls -> REST calls: 0
feed stopped + cache cleared -> get_price = 75921.8 in 181ms, REST calls: 1
injected stale price 1.0 -> refused (0.5s old, max 0.3s), REST fallback, price 75921.8
pending asyncio tasks after stop: 0
```

### کش کندل — چطور اسکن‌ها polling از REST را متوقف می‌کنند

قیمت‌ها فقط نیمی از ماجرا بودند. هر اسکن استراتژی هنوز برای هر تایم‌فریم `GET /api/v1/futures/market/kline` صدا می‌زد. حالا `get_candles()` از `KlineCache` تغذیه‌شده توسط کانال‌های `market_kline_<interval>` عبور می‌کند.

**فریم هیچ فیلد زمانی ندارد.** در ۲۰۲۶-۱۱-۰۷ به‌صورت زنده تأیید شد که push کانال `market_kline_1min` این است:

```json
{"ch":"market_kline_1min","symbol":"BTCUSDT","ts":1794011946619,
 "data":{"o":"75915.9","c":"75915.9","h":"75915.9","l":"75915.8","b":"0.0378","q":"2869.62094"}}
```

`data` دقیقاً `o/h/l/c/b/q` دارد — **هیچ `time`ی ندارد**. اندپوینت REST کندل *time* برمی‌گرداند. پس زمان باز شدن کندل با گرد کردن `ts` فریم به مرز بازه محاسبه می‌شود:

```
open_time = (ts_ms // interval_ms) * interval_ms
```

اگر این را اشتباه کنید، همهٔ کندل‌ها روی یک کلید جمع می‌شوند و سری هرگز رشد نمی‌کند — بی‌صدا و بدون خطا.

**جایگزینی در مقابل افزودن.** کانال کندل *در حال شکل‌گیری* را هر ۵۰۰ میلی‌ثانیه دوباره push می‌کند. کش وقتی زمان باز شدن یکسان است آخرین کندل را **جایگزین** می‌کند و وقتی زمان باز شدن جدیدتر رسید **اضافه** می‌کند. افزودن کورکورانه سری را هر ۵۰۰ms یک عضو بزرگ‌تر می‌کرد و همهٔ اندیکاتورها را خراب می‌کرد.

**کهنگی مضربی از بازه است، نه ثانیهٔ ثابت.** کندل ۱ دقیقه‌ای به‌طور مشروع ۶۰ ثانیه قدیمی است؛ کندل ۱ روزه ۲۴ ساعت. مجموعهٔ کندل وقتی کهنه است که زمان باز شدن جدیدترین کندل قدیمی‌تر از `KlineCache.max_age_mult` × بازه باشد (پیش‌فرض ۲×).

| وضعیت | چه اتفاقی می‌افتد |
|---|---|
| سری تازه، به‌اندازهٔ کافی بلند و تغذیه‌شده از WS | برگردانده می‌شود، `source=ws`، **بدون فراخوانی REST** |
| جدیدترین کندل قدیمی‌تر از `max_age_mult` × بازه | **رد می‌شود**، هشدار، بازگشت به REST، `stale_rejection` |
| کندل کمتر از نیاز فراخوان | **رد می‌شود**، بازگشت به REST، `short_series` — سری کوتاه سیگنال غلط می‌دهد که بدتر از سیگنال کند است |
| کش فقط کندل‌های اولیه از REST دارد | بازگشت به REST (نمی‌توان ادعا کرد زنده است) |
| WS قطع است | بازگشت به REST؛ موتور ادامه می‌دهد |
| `MARKET_DATA_SOURCE=rest` | هیچ کشی خوانده نمی‌شود، **هیچ سوکتی باز نمی‌شود** |

**گرم‌کردن (Warmup).** WS فقط از لحظهٔ اشتراک کندل می‌دهد، پس یک استراتژی ۲۰۰ کندلی به ۲۰۰ دقیقه uptime نیاز دارد. هنگام شروع، کش **یک بار** برای هر `(symbol, interval)` از REST پر می‌شود؛ بنر تعداد فراخوانی‌ها را گزارش می‌کند. مجموعهٔ اشتراک از تایم‌فریم‌های تنظیم‌شده (به‌علاوهٔ `5m` که ATR استاپ متحرک می‌خواند) مشتق می‌شود، نه یک فهرست hardcode.

تأیید زنده (`scripts/verify_ws_klines.py`، فید واقعی):

```
market data: ws (connected, 1 symbols)
kline timeframes subscribed: ['1m', '5m']
warmup REST calls: 2
RAW: {"ch": "market_kline_1min", "symbol": "BTCUSDT", "ts": 1794011946619, "data": {...}}
get_candles('BTCUSDT','1m',200) -> 200 candles, cache src=ws
closes seen for open=1794011940000: [75915.9, 75915.8, 75915.7, 75915.6]
same open time (replaced, not appended): True   count stable: True
open time advanced: True   count grew by exactly one: True (delta=1)
20 get_candles calls -> REST kline calls: 0
feed killed + cache cleared -> 200 candles in 212ms, REST kline calls: 1
frozen cache -> refused (62s old, max 0s), REST fallback
short series (50 candles, want 200) -> refused, REST fallback
MARKET_DATA_SOURCE=rest -> WS connect attempts: 0
pending asyncio tasks after stop: 0
```

### جزئیات Heartbeat

کلاینت `{"op":"ping","ping":<unix seconds>}` می‌فرستد و سرور پاسخ می‌دهد `{"op":"ping","ts":...,"pong":<echoed>,"ping":<server seconds>}`. سرور خودش ping **نمی‌فرستد** (تأییدشده: ۴۵ ثانیه بی‌کاری، صفر فریم)، پس کلاینت باید آن را هدایت کند. نبودن pong در بازهٔ `pong_timeout` سوکت را می‌بندد تا اتصال مجدد اجباری شود.

## ماندگاری

تنظیمات و حالت یادگیری پس از ری‌استارت می‌مانند. یک ماژول همه را مدیریت می‌کند: `jrock/store.py`، با پشتیبانی `data/state.json` (نسخه‌دار) و `data/memory.jsonl` (محدود).

**اولویت صریح است: store ماندگار > `.env` > پیش‌فرض داخلی.** مقداری که در زمان اجرا تغییر کند *در همان فراخوانی* روی دیسک نوشته می‌شود، پس `kill -9` نمی‌تواند آن را گم کند. `.env` فقط به‌عنوان آینهٔ راحتی همگام می‌شود و هرگز نمی‌تواند بر store پیروز شود.

چه چیزی ماندگار می‌شود: هر مقدار موتور که در زمان اجرا قابل تنظیم است (اهرم، پارامترهای ریسک، نمادها، تایم‌فریم‌ها، بازهٔ اسکن/گزارش، مدیریت میانی، بازگشتی، ...)، سطح تفکر عامل و منبع دادهٔ بازار، وضعیت مدیریت پوزیشن (`breakeven_done`، `trailing_stop`، `peak_roi`، `partial_done`)، شمارنده‌ها و حافظهٔ یادگیری (بازخورد / رویدادها / واقعیت‌ها).

**Autotrade و حلقهٔ موتور ثبت می‌شوند اما هرگز خودکار از سر گرفته نمی‌شوند.** بعد از کرش، بنر صریح می‌گوید؛ شما با `start trading` آگاهانه دوباره روشن می‌کنید. راه‌اندازی مجدد بی‌صدای جریان سفارش زنده، همان حالت شکستی است که این موتور نباید داشته باشد.

ویژگی‌های ایمنی:

- **نوشتن اتمی** — فایل موقت + `fsync` + `os.replace` + `fsync` دایرکتوری. کرش وسط نوشتن یا فایل قدیمی را می‌گذارد یا جدید را، هرگز فایل ناقص.
- **نسخه‌بندی طرح** — فیلد `version` با مسیر مهاجرت. فایل v1 در جا ارتقا می‌یابد، دور ریخته نمی‌شود.
- **بازیابی از خرابی** — فایل ناخوانا به `state.json.corrupt-<timestamp>` پشتیبان‌گیری می‌شود، هشدار ثبت می‌شود و موتور تمیز شروع می‌کند. هرگز هنگام شروع کرش نمی‌کند و هرگز بی‌صدا پاک نمی‌کند.
- **رازها هرگز روی دیسک نمی‌روند** — نام کلیدهای راز قاطعانه رد می‌شود و هر *مقدار* راز ثبت‌شده‌ای که در payload پیدا شود، نوشتن را متوقف می‌کند. کلیدهای API فقط در `.env` زندگی می‌کنند.

```
/memory              تعداد ورودی، اندازه روی دیسک، آخرین نوشتن، ورودی‌های اخیر
/memory <query>      جستجو
/memory clear        اول می‌پرسد؛ /memory clear confirm پاک می‌کند
/status              مسیر store، نسخهٔ طرح، آخرین ذخیره، اندازه
```

خودتان تأیید کنید:

```bash
python scripts/verify_store.py     # SIGKILL، اولویت، خرابی، مهاجرت، اسکن راز
python scripts/verify_restart.py   # همان از مسیر واقعی فرمان عامل
```

## پیش‌بررسی سفارش: چرا 20003 و 30029 دیگر به صرافی نمی‌رسند

دو رد شدن از سوی صرافی ریشه در این داشت که موتور درخواست‌هایی می‌فرستاد که می‌توانست محلی رد کند.

### 30029 `SL price must be less than mark price`

این خطا **دو** علت مستقل داشت. اصلاح اول (58f901c) فقط اولی را بست و به همین دلیل خطا روی یک سفارش زندهٔ AKEUSDT برگشت.

**علت ۱ — برنامهٔ ورود قیمت مارک را نادیده می‌گرفت.** موتور حد ضرر را از **قیمت ورود (آخر)** حساب می‌کرد و هرگز **قیمت مارک** را نمی‌گرفت. باینکس تریگر را با قیمت مارک اعتبارسنجی می‌کند، پس وقتی مارک پایین‌تر از آخرین قیمت بود، استاپ در سمت اشتباه می‌افتاد و کل سفارش رد می‌شد.

**علت ۲ — مسیر موتور در حال اجرا اصلاً اصلاح نشده بود.** `plan_tpsl` مارک‌آگاه شده بود، اما حلقهٔ مدیریت (`manage_positions`: سر‌به‌سر و استاپ متحرک) حد ضرر خودش را با `round_price(..., 4)` ثابت می‌ساخت و هرگز قیمت مارک نمی‌گرفت. روی AKEUSDT (`quotePrecision: 6`، قیمت حدود ۰.۰۰۵) گرد کردن به ۴ رقم اعشار `0.005051` را به `0.005100` تبدیل می‌کند — بالاتر از مارک — و صرافی پاسخ می‌دهد:

```
[30029] SL price must be less than mark price: 0.0051
```

آن `0.0051` اثر انگشت است: **چهار رقم اعشار روی نمادی که با شش رقم معامله می‌شود.**

اصلاح:

- `risk.clamp_sl()` / `risk.clamp_tp()` حالا **تنها** جایی هستند که TP/SL ایمن می‌شود و هر مسیری که یکی می‌فرستد از آن‌ها عبور می‌کند — برنامهٔ ورود *و* حلقهٔ مدیریت. گرد کردن جهت‌آگاه است (استاپ لانگ به پایین، استاپ شورت به بالا گرد می‌شود) تا گرد کردن فقط استاپ را *دورتر* از مارک ببرد، هرگز آن‌سویش.
- `round_price()` نیم‌به‌بالا است، نه گرد کردن بانکی پایتون که همان فاصله را در هر دو جهت می‌گرد کند.
- `manage_positions` برای هر پوزیشن قیمت مارک را **تازه** می‌گیرد و قبل از ارسال دوباره clamp می‌کند؛ `try_enter` بلافاصله قبل از درخواست مارک را دوباره می‌خواند و clamp می‌کند تا پنجرهٔ حرکت مارک در رفت‌وبرگشت‌های پیش‌بررسی بسته شود.
- `format_price()` دیگر با `round()` دوباره گرد نمی‌کند، چون می‌توانست clamp را بعد از اعتبارسنجی خنثی کند.
- وقتی قیمت مارک قابل دریافت نیست، جایگزین آخرین قیمت است که با دامنهٔ حفاظت قیمت نماد در جهت ایمن گسترده شده — نه آخرین قیمت خام که می‌تواند سمت اشتباه مارک باشد.
- `validate_tpsl_side()` قواعد مستند 30020-30033 و 30024/30025 (سمت لیکویید) را برای هر دو جهت پوشش می‌دهد و روی مقادیر دقیقی که فرستاده می‌شوند دوباره اجرا می‌شود.
- `build_order_body` محلی با ذکر نماد، جهت، قیمت SL، قیمت مارک و قاعدهٔ نقض‌شده رد می‌کند.
- اگر هیچ استاپ معتبری وجود نداشته باشد (اهرم بالا + تیک درشت)، `TpSlSideError` قیمت لیکویید و محدودیت را نام می‌برد، نه این‌که استاپ نامعتبر بفرستد.

### 20003 `Insufficient balance`

دو علت مستقل، هر دو حالا قبل از ارسال گرفته می‌شوند:

1. **پله، اهرم را سقف می‌زند.** `get_position_tiers` مقدار `leverage` را برمی‌گرداند که *حداکثر* برای آن بازهٔ نوشنال است (AKEUSDT: ۵۰x زیر ۱۰ هزار، ۲۵x زیر ۲۰ هزار، ۱۰x زیر ۸۰ هزار). درخواست بیشتر باعث می‌شود صرافی مارجین بیشتری از محاسبهٔ موتور بخواهد — که به‌صورت 20003 ظاهر می‌شود، نه خطای اهرم. پیش‌بررسی حالا اهرم موتور را با پله مقایسه می‌کند.
2. **هیچ بررسی موجودی نبود.** پیش‌بررسی مارجین لازم را با موجودی واقعی قابل‌استفاده مقایسه می‌کند و با ذکر هر دو عدد رد می‌کند.

محدودیت‌های قابل‌تنظیم (همه پیش‌فرض `0` = غیرفعال، پس رفتار قبلی تغییر نمی‌کند):

| متغیر | معنی |
|---|---|
| `MIN_MARGIN_USDT` | رد سفارش‌هایی که مارجینشان کمتر از این است |
| `MAX_MARGIN_USDT` | رد سفارش‌هایی که مارجینشان بیشتر از این است |
| `MAX_NOTIONAL_USDT` | رد سفارش‌هایی که نوشنالشان بیشتر از این است |
| `ORDER_UNIT` | `QUANTITY` (پیش‌فرض)، `NOTIONAL` یا `COST` |

هر چیز دیگری که از استاپ محافظت می‌کند در کد ثابت است و قابل‌تنظیم نیست: تریگر همیشه `LAST_PRICE` است، استاپ حداقل فاصلهٔ `MIN_STOP_TICKS` (۳) تیک قیمتی از قیمت تریگر نگه می‌دارد و قیمت تریگر قبل از هر نوشتن TP/SL دوباره خوانده می‌شود. یک تنظیم، یک معنی.

تأیید با دادهٔ زنده: `python scripts/verify_tpsl_side.py`

## چهار روش TP/SL

این‌ها همان چهار روش مقالهٔ رسمی آکادمی *«Bitunix Futures Positions: Guide to Four TP/SL Methods»* هستند. دو روش شکل خروج بومی پوزیشن جدید را انتخاب می‌کنند (`TPSL_METHOD`)؛ دو روش دیگر همیشه در حلقهٔ مدیریت مسلح‌اند و انتخابگر ندارند — مسلح کردنشان یک انتخاب نیست.

| روش | کار | اندپوینت | اعمال‌کننده | کد |
|---|---|---|---|---|
| `POSITION` | یک TP/SL **کل** پوزیشن را می‌بندد | `POST /api/v1/futures/tpsl/position/place_order` | صرافی | `client.py` `place_position_tp_sl_order` |
| `PARTIAL` | هر پلهٔ `share@R` یک TP بومی مستقل با `tpQty` است و روی نقطهٔ ورود پارک می‌شود | `POST /api/v1/futures/tpsl/place_order` | صرافی | `engine.py` `_place_partial_rungs` |
| `TRAILING` | سر‌به‌سر، سپس دنبال کردن قیمت — همیشه روشن | ندارد — نرم‌افزاری | حلقهٔ مدیریت | `tpsl.py` `next_trailing_stop` |
| `ACCOUNT` | وقتی سود/زیان کل از آستانهٔ USDT عبور کند **همهٔ** پوزیشن‌ها را می‌بندد — همیشه روشن | ندارد — نرم‌افزاری | حلقهٔ مدیریت | `account_tpsl.py` `account_tpsl_decision` |

**هشدار صادقانه:** `POSITION` و `PARTIAL` توسط صرافی اعمال می‌شوند، پس در خاموشی موتور هم زنده می‌مانند. `TRAILING` و `ACCOUNT` اندپوینت بومی ندارند — نرم‌افزاری‌اند و فقط وقتی حلقهٔ مدیریت در حال اجراست فعال می‌شوند.

`PARTIAL` دلیل وجود `tpQty`/`slQty` در `place_tp_sl_order` است: اندپوینت موقعیت **هیچ فیلد مقداری ندارد**، پس فقط می‌تواند کل پوزیشن را ببندد. خروج پله‌ای فقط با اندپوینت مستقل ممکن است.

```
tpsl method PARTIAL            # انتخاب شکل خروج بومی
partial ladder 40@1,35@2,25@3  # PARTIAL: ۴۰٪ در 1R، ۳۵٪ در 2R، ۲۵٪ در 3R
partial ladder off             # بدون پله: بازگشت به POSITION
account tp usdt 100            # ACCOUNT: بستن همه در +۱۰۰ USDT کل
account sl usdt 50             # ACCOUNT: بستن همه در -۵۰ USDT کل
```

## نردبان PARTIAL — خروج پله‌ای بومی

هر پله یک `/tpsl/place_order` بومی مستقل با `tpQty` است که یک بار هنگام ورود فرستاده و روی صرافی پارک می‌شود. اگر موتور بمیرد، پله‌ها همچنان پر می‌شوند.

```
PARTIAL_TP_LADDER=40@1,35@2,25@3
```

| پله | تریگر | می‌بندد |
|---|---|---|
| 1 | قیمت در 1R | ۴۰٪ پوزیشن |
| 2 | قیمت در 2R | ۳۵٪ |
| 3 | قیمت در 3R | ۲۵٪ |

`R` فاصلهٔ ورود تا حد ضرر است که هنگام ورود ثبت می‌شود، بنابراین هدف‌ها با حرکت استاپ جابه‌جا نمی‌شوند. مجموع سهم‌ها باید `<= 100` باشد و R از چپ به راست افزایش یابد؛ مشخصات غلط رد می‌شود (`Invalid ladder: ... Nothing changed.`) و نردبان در حال اجرا دست‌نخورده می‌ماند. پله‌ای که صرافی آن را خیلی کوچک رد کند با پلهٔ بعدی ادغام می‌شود؛ اگر همهٔ پله‌ها زیر `minTradeVolume` باشند، موتور به یک TP کل‌پوزیشن در دورترین هدف برمی‌گردد تا پوزیشن هرگز فقط با حد ضرر رها نشود.

### قواعد اعمال‌شده در کد، نه فقط مستند

- **سهم‌ها از پوزیشن اولیه‌اند**، هرگز از باقی‌مانده. پوزیشن ۱۰۰۰ واحدی با بستن ۴۰/۳۵/۲۵ مقدار ۴۰۰/۳۵۰/۲۵۰ را می‌بندد و چیزی باقی نمی‌گذارد.
- **تریگرهای افزایشی.** پله‌های بی‌ترتیب رد می‌شوند، نه مرتب — مرتب کردن بی‌صدای یک مشخصات، یک تایپو را پنهان می‌کند.
- **پارک‌شده هنگام ورود، یک بار.** پله‌ها با ورود فرستاده می‌شوند و در هر اسکن دوباره مشتق نمی‌شوند، پس ری‌استارت نمی‌تواند آن‌ها را تکرار کند.

### فرمان‌ها

```
/tpsl                          # روش + نردبان + آستانه‌های حساب
tpsl method PARTIAL            # انتخاب شکل خروج بومی
partial ladder 40@1,35@2,25@3  # تنظیم (اعتبارسنجی‌شده؛ مشخصات غلط چیزی را عوض نمی‌کند)
partial ladder off             # بدون پله
account tp usdt 100            # آستانهٔ TP حساب
account sl usdt 50             # آستانهٔ SL حساب
```

### هر پله چه می‌فرستد

```
POST /api/v1/futures/tpsl/place_order
{"symbol": "BTCUSDT", "positionId": "...", "tpPrice": "...",
 "tpStopType": "MARK_PRICE", "tpOrderType": "MARKET", "tpQty": "..."}
```

**هشدار، صریح:** سفارش‌های پله توسط صرافی اعمال می‌شوند، اما استاپ متحرک و آستانه‌های حساب نرم‌افزاری‌اند. اگر موتور خاموش باشد، پله‌ها و حد ضرر کار می‌کنند؛ ratchet نه.

تأیید: `tests/test_four_tpsl_methods.py` قالب سیم را تضمین می‌کند.

## چهار حالت TP/SL و سه واحد سفارش

### چهار حالت TP/SL

`place_order` برای هر یک از TP و SL دو enum مستقل می‌گیرد که چهار ترکیب مستند می‌سازد:

| فیلد | مقادیر | تعریف در |
|---|---|---|
| `tpOrderType` / `slOrderType` | `LIMIT`، `MARKET` | `order_builder.py:39` `ORDER_PRICE_TYPES` |
| `tpStopType` / `slStopType` | `MARK_PRICE`، `LAST_PRICE` | `order_builder.py:40` `STOP_TYPES` |

| # | `tpOrderType`/`slOrderType` | `tpStopType`/`slStopType` |
|---|---|---|
| 1 | `LIMIT` | `MARK_PRICE` |
| 2 | `LIMIT` | `LAST_PRICE` |
| 3 | `MARKET` | `MARK_PRICE` |
| 4 | `MARKET` | `LAST_PRICE` |

همهٔ چهار حالت در `build_order_body` (`order_builder.py:152-157`) اعتبارسنجی می‌شوند و توسط `OrderSpec.to_body` (`order_builder.py:79-81`) در بدنه قرار می‌گیرند. مسیر ورود خود موتور از حالت ۳ (`MARKET`/`MARK_PRICE`) در `engine.py:826-828` استفاده می‌کند.

### سه واحد سفارش

طبق مقالهٔ رسمی *«Explanation of the Order Units in Futures Trading»*، باینکس سه واحد ارائه می‌دهد. هر سه در `risk.py:171` `ORDER_UNITS` پیاده‌سازی و توسط `qty_from_unit` (`risk.py:174`) تبدیل می‌شوند:

| واحد | معنی | تبدیل |
|---|---|---|
| `QUANTITY` | مقدار ارز پایه | `qty = amount` |
| `NOTIONAL` | ارزش پوزیشن به USDT | `qty = amount / price` |
| `COST` | مارجین پرداختی به USDT | `qty = amount * leverage / price` |

قالب سیم **همیشه** `qty` به ارز پایه است — واحد فقط نحوهٔ بیان اندازه را عوض می‌کند. `ORDER_UNIT` آن را انتخاب می‌کند؛ `QUANTITY` پیش‌فرض و بی‌اثر است، پس رفتار تاریخی تغییر نمی‌کند.

### تریگر با کدام قیمت مقایسه می‌شود

`LAST_PRICE` (پیش‌فرض باینکس)، در کد ثابت (`engine.py` `TRIGGER_TYPE`) و دقیقاً در یک جا خوانده می‌شود — `get_trigger_price()`. هم اعتبارسنجی محلی پیش‌بررسی و هم `tpStopType`/`slStopType` که روی سیم می‌رود از همان ثابت می‌خوانند، پس نمی‌توانند از هم جدا شوند. صرافی TP/SL را هنگام رسیدن درخواست با قیمت تریگر انتخابی اعتبارسنجی می‌کند و استفاده از `LAST_PRICE` با منطق مدیریت خود موتور و مبنای ROI گزارش هم‌خوان است.
